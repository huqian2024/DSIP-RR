## 1. 与两个旧数据集的区别（重要：旧数字被取代）

| 数据集 | 计划 `w` | demand | 状态 |
|---|---|---|---|
| `results/psl_matrix`（450 run） | **13.9**（路段限速标定） | matrix demand | 计划侧**诊断**实验，保留；不进交通侧主表 |
| `results/psl_tr`（15+15，pilot） | 7 | **旧的** demand 版本 | **被本矩阵取代**（见 §2） |
| `results/psl_traffic`（本矩阵 45+45） | **7**（上游硬编码值） | matrix demand | **交通侧正式数据** |

取代理由有两条，均为实测，不是偏好：

1. **demand 版本不一致**。pilot 的 `vehicleArrival.json` 与矩阵的不同（md5 不同），
   请求数 2376 vs 2378；由此产生的计划在车辆层面差异很大——
   3165 个共同车辆中 **2284 辆的 `in_time` 相差 > 1 s**，最大 548 s。所以 pilot 的
   执行结果不能与 450-run 矩阵当作同一配置。
2. **`w` 必须回到上游默认 7**（见 §2）。

## 2. 为什么执行层用 `w = 7`（否定 `w = 13.9`）

`w` 只改适配器的占用模型 `Li/w + Li/v`；求解器二进制始终用硬编码的 7。
2026-11-14 为了抬高**计划侧**完成率用了 `w = 13.9`，但作者已把计划侧降级为诊断量；
在**执行层**实测，`w = 13.9` 的时刻表明显不可执行：

| cross3, seed 81890 | w = 7（pilot 计划） | w = 13.9（矩阵计划） |
|---|---|---|
| 进入偏差 p50, d1 / d3 / d5 | **20.7 / 23.6 / 26.5 s** | 37.4 / 41.2 / 41.1 s |
| 近距事件 (<1.5 m), d1 / d3 / d5 | **55 / 46 / 55** | 71 / 76 / 103 |
| 完成行程, d1 | 1932 | 1750 |

（原始产物：`results/psl_tr/exec-d{1,3,5}-s81890` 为 `w = 7`，
`results/psl_tr2/psl-cross3-d{1,3,5}-s81890` 为 `w = 13.9`；两者都已 git-ignored，可重算。）

机制：`w = 13.9` 等于假设车辆以路段限速**匀速**穿过冲突区（占用 0.72 s），
而执行器是从**静止**重新起步（`setStop`/`resume`），实际清空要 2–3 s。
把车按 0.72 s 间隔打包，执行时必然堆积。

⇒ 执行层采用 **`w = 7` = 上游硬编码值，适配器零标定**，这是最可辩护的选择；
`--w 13.9` 作为已记录的敏感性保留，**两者永不混表**。

> 注意：`w = 13.9` 在 d3/d5 上完成行程更多（2532 / 2477），但近距事件也更多
> （76 / 103），且进入偏差翻倍。以"多跑几辆车"为由选它，同时又要拿近距事件做对比，
> 是不正当的；故不采用。

## 3. 协议（与 450-run 计划矩阵严格同源）

| 项 | 取值 |
|---|---|
| 路网 | `cross2` / `cross3` / `cross4`（两向 4 / 6 / 8 车道） |
| 密度 | `lanes{L}_density{1..5}.rou.xml`（Table I，MinD–MaxD，1:2:1） |
| seeds | `81890 / 81891 / 81892` |
| 仿真 | 1000 s，`--step-length 0.1`，`types.typ.xml` |
| demand | **复用** `results/psl_matrix/demand/{net}_d{D}_s{S}`（`flow_resample`） |
| 计划 | 复用实例 `results/psl_matrix/instances/{net}_trim`，`--packer psl --w 7 --window-size 40 --horizon 1000` |
| 指标 | `main.tex` §III-B：活动车队平均 timeLoss / 平均速度，**10 s** 采样；近距 = `--collision.mingap-factor 0.5`（minGap 3.0 × 0.5 = **1.5 m**）；紧急制动取自 SUMO 警告（阈值 = vType `decel` 4.5 m/s²） |
| 对照 | `--control none`，同 net / 同 rou / 同 seed |

**重复次数**：45 cell × 2 控制 = **90 run**。

## 4. 复现

```bash
python3 baselines/psl_sumo/run_traffic_matrix.py \
  --out-root results/psl_traffic \
  --nets cross2,cross3,cross4 --densities 1,2,3,4,5 --seeds 81890,81891,81892 \
  --w 7

python3 evaluation/psl_baseline_report.py \
  --nets cross2,cross3,cross4 --densities 1,2,3,4,5 \
  --seeds 81890,81891,81892 --w 7 \
  --out-dir evaluation/figures/psl_traffic
```

驱动是**逐步可续跑**的：已存在的产物会被跳过，中断后重跑即可。
每 cell 约 20 s（计划+校验+两次 1000 s 仿真）。

### 5.3 四条可报告的结论（其余一律不得据此外推）

1. **近距交互近似减半，方向一致**：3 个路网 × 5 个密度共 15 格全部下降
   （cross2 156→54、cross3 105→57、cross4 93→48）。紧急制动同步下降（316→100 等）。
2. **逐车 timeLoss 上升**：cross3 +48 %（10.13→15.01 s）、cross4 +53 %（9.42→14.45 s）、
   cross2 +13 %（18.61→21.12 s）。**必须同时报告**，不能只报近距。
3. **平均速度下降**：7.34→6.04 m/s（cross3 d1）等，与"停走执行"一致。
4. **时刻表不可精确执行**：进入偏差 p50 **22.1–29.7 s**，且随密度单调上升
   （cross4：22.1→29.7 s）。**任何表述都不得写成"按计划执行"。**

### 5.4 三个必须在论文里披露的混杂

1. **已插入车辆少 25–35 %**：cross3 d1 「2718 → 1928」。停走保持把车压回进口，
   阻塞后续插入。论文指标是**活动车队**的平均值，因此"平均 timeLoss 上升"里混有
   "车队构成变化"，两者不可分离——只能并列报告 `inserted` / `trips`。
2. **cross2 的无控制基线本身已接近饱和**（TLser 11.8–12.7 s，是 cross3 的 1.8 倍），
   所以 PSL 在 cross2 上只把 TLser 抬高 13–15 %，而在 cross3/cross4 上抬 48–53 %。
   跨路网比较时不能把这当成"PSL 在宽路上更差"的证据。
3. **seed 方差不可忽略**：cross3 d1 的 PSL TLser 在 3 seeds 上为 **9.69 / 9.89 / 25.90**。
   3 seeds 只够满足闸门，**不足以支撑置信区间**；正式对比建议 ≥10 seeds（见 §6）。

### 5.5 不能说的话

- ❌ "PSL 提升了通行能力" —— 速率没有提升，插入数反而下降。
- ❌ "PSL 优于/劣于 DSIP" —— 冲突模型不同、无配对重跑（`fairness-protocol.md` §7.2）。
- ❌ 把本表与 `results/psl_matrix`（`w = 13.9`）的计划侧完成率放在同一张表里。
