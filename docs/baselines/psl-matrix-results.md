## 2. 【必须先说明】需求是怎么取的，以及为什么不能用 SUMO 回读

第一版用"无信号控制的 SUMO 参考运行"回读插入车辆，结果发现：

```text
density 5, cross3, 300 s:  Inserted 828 / Loaded 2400,  Waiting 1572
density 1 vs 5 的协调车数:  2026 vs 2063   ← 密度维度塌缩
```

原因是进口边只有 86 m × 3 车道，队列装不下高密度需求；插入被**存储容量**卡住，
与被评估算法无关。若照此回读，MaxD 的需求会退化成 MinD。

⇒ 改为 **`--reference-source flows`**：直接按 `<flow departInterval="normal(μ,1)">`
重采样出发过程（每个 flow 用其自身 `seed` 作 RNG 种子，可复现）。
**需求 = flow 定义的过程，而不是 SUMO 恰好能插入的子集。**

记录为 `demand_source: flow_resample`。这是相对"从 SUMO 回读"的**有据偏离**，
但不改变需求强度：修正后 d1→d5 的协调车数为 2378 → 5570（2.34×），与 Table I 的
2.5× 密度跨度一致。

### 3.1 三条读得住的结论

1. **达成速率与密度无关**：2/3/4 车道分别恒定在 **1.45 / 1.99 / 1.8** veh/s，
   而需求从 1.59 涨到 6.97 veh/s。⇒ 这是一个**容量上限**，不是一个"随密度缓慢退化"的性能曲线。
2. **完成率随密度单调下降**，且**种子间波动极小**（±1–2 个百分点，30 个种子）
   ⇒ 表格可作为论文中的 PSL 基线数字，重复性充分。
3. **容量不随车道数扩展、甚至下降**（1.45 → 1.99 → 1.8）。
   因为适配层每个运动只建一条**中位车道路径**，而需求按每车道密度线性增长。
   ⇒ 这是本适配层最需要在论文里交代的结构性限制。

| 项 | 值 |
|---|---|

| 独立校验 | **450 / 450 `ok = True`** |
| **冲突违规总数** | **0** |
| **核验的冲突顶点对数** | **1,705,046,441**（17.05 亿） |
| CPLEX 批次 | **43,088 批 `optimal`** |
| 求解器崩溃批次 | **59**（占 0.14 %），分布在 54 个 run，集中在 HigD/MaxD |
| 总墙钟时间 | 3,443 s（8 并行，单机） |

> **59 个崩溃批必须如实说明**：上游 `PTNode::writeToFile`（`PTNode.cpp:9-30`）在 PBS
> 无解时对空 `plan[i]` 取 `[0]`，会段错误。适配层检测到后按"退回原始 ETA → 再失败则该窗口
> 跳过"降级（`solve_window`）。被跳过的窗口内约 40 辆/窗 × 59 ≈ 2.4 千辆未排程，
> 占 171 万辆的 **0.14 %**，对本表结论无实质影响，但**不能隐藏**。

## 5. 不能写进论文的东西（与已完成部分并列）

- **吞吐 / 平均行程时间 / 碰撞数**：没有 SUMO 执行层（`setStop`/`resume` 回灌），
  本矩阵是**计划表**，不是交通仿真。`output_kind = schedule_only`。
- **"PSL 弱于/强于 DSIP"**：图实例是自建的、冲突模型不同，且 DSIP 的历史结果没有同口径重跑。
- **右转的协调效果**：右转在四路交叉中没有内部交叉点，按自由流排程，
  `schedule.csv` 里标 `coordinated=False`。
