## 3. 【关键发现 F1】入口/出口折叠使模型容量低于稿件最低密度

上游把**同一进口的所有车道折叠成一个入口冲突点**（`WSR_0` 与 `WER_0` 同 `pos`）。
按此模型，一个进口的通行能力是

```
1 / (Li/w + Li/v)  ，w = 7，v = 15（LP 上界）
  直行 Li=5.00 → 1.05 s
  左转 Li=10.07 → 2.11 s
  右转 Li=11.72 → 2.45 s
```

按 1:2:1 加权（实测 1.69 s/veh）⇒ **≈0.60 veh/s/进口 = 2160 veh/(h·进口)**。

Table I 的 **MinD** 是 480/240/240 veh/(h·lane)，3 车道 ⇒ 每进口 **0.80 veh/s**。
⇒ **最低密度就是该模型容量的 133%。**

这不是 PSL 的性能结论，而是**适配层图模型的容量天花板**：上游只在 5–25 辆的窗口里用它，
从未面对过这种需求。

## 4. 【处理】`--trim-ends`：轨迹只保留真实交叉点

理由（三点，都不是为了好看）：

1. **几何上更忠实**：不同车道的停止线是**互相独立**的物理位置，把整个进口塌缩成一点是上游的简化，
   不是真实约束。删掉入口/出口顶点后，"同进口车辆不能同时进入"这一人为限制消失。
2. **入口/出口点不携带任何交叉信息**：它们只记录"同进口/同出口"，属于合流/跟驰，
   SUMO 的 IDM 与内部连接已经处理；把它塞进冲突求解器只会制造虚假瓶颈（即 F1）。
3. **顶点预算仍安全**：cross3 从 56 降到 **32**（预算 104）。

**代价与处理**：右转运动在我们的几何里**没有任何内部交叉点**（与稿件 Table II"右转常绿"一致），
因此没有可规划的顶点 ⇒ 不进入 PSL 批次，按自由流直接排程，并在 `schedule.csv` 里标
`coordinated = False`。这必须在论文中说明，不能假装它们被 PSL 协调过。

### 5.1 这不是 PSL 的锅——三个对照实验

| 实验 | 结果 | 说明 |
|---|---|---|
| **`--packer greedy`（完全不用求解器，纯 ETA 顺序 + 同一守卫）** | **1.461 veh/s** | 与 PSL 的 1.60 基本相同 ⇒ **不是求解器的排序能力问题** |
| 窗口 40 → 60 → 80 → 120 | 1.42 / 1.46 / 1.44 / 1.40 veh/s | **窗口放大无效** |
| `--lane-mode per-lane`（每条内车道一条路径，100 顶点） | 1.393 veh/s，调度结束 1495 s | **更差**：冲突点从 16 组涨到 32 组，合取约束更重 |
| 冲突组占用率（movement 图） | 最高 **46–55 %**，无组 > 100 % | **不是单组容量打满** |

⇒ 瓶颈是**"一辆车必须依次穿过 4 个冲突点"的合取结构**，配合上游硬编码的占用公式

```text
占用 = Li/w + Li/v     w = 7（SIPP.h:79）
   直行 Li=5.00  → 1.074 s
   左转 Li=10.07 → 2.162 s
```

按 MinD 的 1:2:1 混合，全需求下各冲突组的**理论占用率约 73–82 %**；
在这种合取资源系统里，单组 80 % 占用已足以让车辆排长队。
**这个公式在二进制里硬编码，无法在不重编译（需要 CPLEX）的情况下改。**

### 5.2 因此：能进论文的与不能进论文的

**可以写**（都是实测、可复现、有 manifest/校验）：

- PSL 在本项目的 cross3/MinD/seed 81890 上，**1000 s 内完成 78.8 % 的协调需求**，
  平均进入延误 **105 s**（已完成车）/ **135 s**（全体），计划侧有效速率 **1.60 veh/s**。
- 该上限**来自上游的冲突点占用模型**，并有 `greedy` 对照与占用率诊断佐证——
  不是适配层的打包缺陷，也不是求解器失败（全部 `optimal`）。

**不能写**：

- 任何吞吐 / 平均行程时间 / 碰撞数（无 SUMO 执行层）。
- "PSL 全面弱于 DSIP"——我们的图实例是自建的，且 DSIP 的冲突模型不同，
  必须同口径重跑后才可比较。
- 把这组数字与历史 DSIP 结果放进同一张统计图。

### 6.1 三条可写入论文的结论

1. **PSL 在上游冲突模型下，MinD 时程内完成率 73.7–78.8 %（三种子均值 76.2 %），
   平均进入延误 105–127 s。** 种子间波动小（±2.5 个百分点），可重复。
2. **这个上限不是 PSL 的排序能力**：同一实例、同一需求，**完全不用求解器**的贪心装填
   得到 77.4 %（PSL 同种子 78.8 %）。⇒ 上限来自冲突模型，不是 PBS/SIPP/LP。
3. **上限与车道数无关**：2/3/4 车道下完成率 70.1 / 76.2 / 70.7 %，而需求随车道数线性增长
   （1.56 / 2.03 / 2.10 veh/s）。⇒ 因为适配层每个运动只建**一条中位车道路径**，
   模型容量不随车道数扩展。这是结构性缺陷，**不能用"再多跑几个密度"绕过**。

### 6.2 为什么"不随车道数扩展"是致命的

`scheduled_rate` 在 2/3/4 车道上是 1.089 / 1.528 / 1.423 veh/s（几乎不变），
而 `demand_rate` 是 1.557 / 2.026 / 2.098 veh/s（随车道数上升）。
⇒ HigD/MaxD 只会更糟，不会更好。**任何"PSL 在更高密度表现如何"的问题，
在这个模型下都无法回答。**

## 7. B 方案评估：不是"改模型"，而是"必须改 C++"

用户要求评估"单元/区域级冲突抽象（B）对上游改动是否过大"。**结论：过大，且不比 A 便宜。**

### 7.1 B 看起来只是换 JSON

如果把顶点从"每个交叉点一对"改成"若干冲突区"，理论上只要
`net_to_graph.py` 生成不同的 `graph.json` + `pairDistance.json` + `vehicleArrival.json`，
C++ 一行都不用改——`Instance::loadSearchGraph` 只读顶点名、`vertex_conflicts`、`pairDistances`；
`PBS.cpp` 只用 `vertex_conflicts` 和 `getConflictPoints(traj[0])[0]`。

### 7.2 但 B 会撞上 `Li` 的硬编码语义

上游的占用公式（`SIPP.cpp:194`、`SIPP.cpp:364-380`）是

```text
占用 = Li(direction, agent_length) / w  +  Li(direction, agent_length) / v
w = 7（SIPP.h:79）；agent_length = 5，来自 Instance.cpp:89 ag.length = 5
Li(straight) = agent_length
Li(left/right) = 4R·asin(agent_length / 2R)
```

**`Li` 只由"车辆长度 + 转向半径"决定，与顶点所代表的几何尺度无关。**
所以它天生就是"一个质点大小的冲突点"的占用模型：

| 抽象 | 单个资源应占用的时间 | 上游公式实际给出 |
|---|---|---|
| 点（现状，27 m 路径上 4 个点） | 1.07–2.16 s | 1.07–2.16 s ✅ 一致 |
| **区（一条 27 m 的整段）** | 27.2/13.9 + 5/13.9 ≈ **2.3 s** | **1.07 s** ❌ 低估 2.1 倍 |

⇒ 用区域抽象但沿用上游公式，会把"整段冲突区"的占用按一个质点计价，
**这是安全上的错误，不只是精度问题**。要修只能在 `SIPP.cpp` 里把 `Li` 改成
"区长度 + 车长"，**必须重编译 ⇒ 需要 CPLEX ⇒ 与 A 同一个阻塞**。

### 7.3 B 与 A 的代价对比

| | A：改 `w` | B：区域抽象 |
|---|---|---|
| 需要改 C++？ | 是（`SIPP.h:79` 一行） | 是（`Li` 的语义，`SIPP.cpp:364-380`） |
| 需要 CPLEX 重编译？ | **是** | **是** |
| 相对上游的偏离 | 一个常数 | **整个冲突表示** |
| 论文可辩护性 | "上游参数按其几何尺度修正，已披露" | "我们换了冲突模型" —— 更接近"不是 PSL 了" |

**⇒ 建议 A，不建议 B。** B 若不改 C++ 就是错的，改了 C++ 则偏离比 A 大得多。

### 7.4 A 需要多大的 `w`？（今天就能算）

把占用缩到 0.75 倍即可把达成率从 0.75 提到 1.0：

```text
直行：5/w + 5/13.9 = 0.75 × 1.074 = 0.806  ⇒  w ≈ 11.2 m/s
左转：10.07/w + 10.07/13.9 = 0.75 × 2.162 = 1.622  ⇒  w ≈ 11.2 m/s
```

⇒ **`w ≈ 11 m/s`（而不是 7）**。7 m/s 是上游机器人场景的穿越速度；11–12 m/s
与本项目 50 km/h（13.9 m/s）的道路限速是同量级，物理上更说得通，但**属于改上游参数，必须披露**。



## 7. 必须随任何 PSL 数字一起引用的限制

- **D1 规划侧，不是交通仿真。** `output_kind = schedule_only`。没有吞吐/行程时间/碰撞数。
- **D2 运动学偏离。** 上游 LP 硬编码 `v ∈ [3,15]`，场景 `maxSpeed = 13.9`。
  `--speed-mode psl` 报上游原值（15）；`limit`（默认）按 13.9 重算；两者的差额必须披露。
- **D3 `kinematic` 模式**（停在停止线、从 0 起步）会让占用膨胀 3–4 倍，实测延误升到
  数千秒——它是"若真的把每辆车都拦停"的上界，不是 PSL 的执行方式。
- **D4 右转不参与协调**（§4），必须在论文中说明。
- **D5 车道抽象**：每个运动取中位车道几何，同运动其它车道的横向偏移未建模。
- **D6 到达时刻是模型量**：FCD/tripinfo 首帧 + 匀加速自由流，不含排队。
- **D7 只跑了 1 个路网 × 1 个密度 × 1 个种子 × 前 20 轮**，不是密度矩阵。
